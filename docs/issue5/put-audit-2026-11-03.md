# Private PUT audit — 2026-11-03

This follows the latest Issue #5 manager comment (`6610862384`). It is an audit,
not a production fix. Only `develop` is changed; no deployment or mutation of

## Privacy and method

The deployed Worker content was read **inside the authorized private tool runtime**
and parsed with Acorn 8.15.0. Worker code was never executed. Only the tested
allowlisted metadata produced by `auditPutSource()` left that runtime. No source
fragments, AST, key names/values, endpoints, subscription credentials, literal
strings or parser error excerpts were returned or saved. The earlier raw-source
security rejection was not retried or bypassed. Source-import readiness remains
blocked; these metadata findings do not replace an approved source export.

The source is minified into one line. Site IDs M1P1–M1P7 and callback ID M1F8 are
stable only within this observed module. See `put-audit-redacted.json`. The call
graph resolves unique local declarations and conservatively includes callbacks;
it does not resolve aliases/dynamic dispatch or prove all feasible execution
paths. A regression test prevents mistaking global `fetch()` for Worker.fetch.
No content equality guard was established by this analysis: this means
**unverified**, not a claim that every possible indirect guard is absent.

P4 is concrete evidence of a per-tick write path that can exhaust the 1,000/day
free write budget on its own. It can also put an avoidable persistence failure
before useful scheduled work. This is stronger than the earlier seven-site count,
but is not a production execution trace or a complete attribution of all usage.
Do not label the earlier list hypothesis as the PUT incident's established cause.

## Conditional daily operation bounds

Use `estimateAuditedPutBudget()`; all numbers below are **attempts under stated
workload assumptions**, not successful writes, billing counters or measured users.

Let C be eligible ticks/day, N the upper bound on devices/records enumerated once
per tick, A the bound on delivery-loop iterations/day that can reach P5/P6,
S state-sync requests/day and T manual test requests/day. For these seven direct
sites, assuming one helper execution per tick and no additional aliased PUTs:

- P4 metadata: at most C (1,440 on the unchanged every-minute cron).
- P7 maintenance: at most C × N, conditional on one visit per enumerated record.
- P5/P6 delivery-state: at most 2 × A; retries must be included in A.
- P3 subscription sync: at most S.
- P1/P2 test work: at most 2 × T.
- Identified cleanup: 0 PUT (DELETE has a separate quota).

Without bounds on S, T, N and A there is **no finite whole-Worker daily upper
bound derived from user count alone**. Pagination, skipped records, repeated cron
events and hidden aliases require further review. This model is not authorization
to change schedules or reduce cron frequency.

| Users, one device each; C=1,440; S=T=0 | Metadata bound | Maintenance bound | Combined bound, A=0 | Combined with A≤C×N×3 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1,440 | 1,440 | 2,880 | 11,520 |
| 2 | 1,440 | 2,880 | 4,320 | 21,600 |
| 100 | 1,440 | 144,000 | 145,440 | 1,009,440 |

The last column is an intentionally conservative **per-tick iteration** cap of
three, including repeated attempts; it does not assert three clinical doses/day
or that each stored alarm is due on every tick. Actual counts may be much lower,
including when the first failed write prevents later sites from running.

## Safe fix options and blockers

1. In an approved private editing environment, remove the unconditional metadata
   PUT from the minute path; keep diagnostic timestamps in non-KV observability.
   Make status/test GETs read-only and bound explicit diagnostic writes. Do not
   call this completed until the real handler is patched and tested.
2. For subscription/schedule sync, use canonical comparison **with serialized or
   transactional ownership/revision control**; do not implement a racy global
   KV get-then-put optimization. Separate stable payload from volatile timestamps.
   Treat expiry renewal as a real state transition: define renewal margin and
   retention policy so suppressing identical writes cannot expire live devices.
3. Await persistence and distinguish validation from transient storage failures;
   return retryable failure (never false saved), with bounded backoff rather than
   a tight loop on the exhausted daily quota. Preserve dedup state after provider
   acceptance and document the external-send/commit crash window.
4. Safe private source option: the owner can provide the export in an approved
   private workspace/secret-separated repository for manual review and patching.
   Do not paste raw source, keys or patient data into this public issue. Only a
   reviewed sanitized source + provenance/hash inventory can satisfy the source
   gate; do not use the metadata report or a mock Worker as that inventory.
5. The local D1 queue stays disconnected. Real API mapping, timezone policy,
   migration, reconciliation, rollback and physical iPhone verification remain
   required. Production source modification/deployment was not performed.
